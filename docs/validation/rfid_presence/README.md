## 최종 결과

- EditMode 118/118 PASS. 주기 범위와 기본값 1초 테스트를 추가했다.
- `runtime.json`: Editor Play 67항목 PASS. `127.0.0.11~14` 출발지 IP의 실제 TCP 클라이언트 4개가 값을 30ms마다 다시 보내 카드가 올려진 상태를 흉내 냈다.
  - 배포 설정 파일을 복사해 쓴 1000ms에서 첫 인식 99ms, 교체 515ms, 제거 1015ms(판정 허용치 각 1300/1300/2300ms). 값은 주기 안의 측정 시점에 따라 달라진다.
  - 같은 값 3.5초 반복 중 선택 상태 변경 없음, 교체 중 빈 상태 없음, 제거 후 연결 유지.
  - JSON을 200ms로 바꾸면 제거 317ms. 범위 밖 값, 키 없음, 파일 없음은 오류를 표시하고 기존 설정을 유지하며 고치면 오류가 사라짐.
  - 이전 RFID-LISTEN-001 항목(수신, 미등록 IP, 재접속, 생성 고정, 매핑, F9/F10)을 새 판단 방식에 맞춰 함께 재실행.
- `f10_panel.png`: 수신 상태 줄의 확인 주기와 판단 안내 문구를 직접 확인. 그림의 값은 테스트 값이다.

최종 콘솔의 오류/경고 15건은 모두 의도한 실패 주입 결과다(미등록 IP2, 포트 점유1, 범위 밖 주기, 키 없음, 파일 없음, 잘못된 HEX, 미등록 블록, 문법 오류 JSON의 메시지와 예외).

## 실행과 변경

`Tools/RFID/verify_tcp_mapping.cs`를 Idle Play에서 Unity execute_code로 실행한다. 저장 테스트는 OS Temp에만 쓰고 종료 시 원래 설정·경로를 복원한다. `format.absentTimeoutMilliseconds`는 이 판단으로 대체되어 제거했고, 기존 JSON에 남아 있어도 무시된다. 이벤트 방식으로 쓰던 스크립트는 값을 반복 전송하도록 고쳤다.

## 미검증

- 실제 리더의 보고 간격. 기본 1초 주기가 적합한지는 이 값에 달려 있다. 테스트의 30ms 전송은 실제 간격이 아니며, 보고 간격이 주기에 가까운 경우의 깜빡임은 시험하지 않았다.
- 실제 RFID 네 대, 현장 망, 방화벽 인바운드, Windows Player 재빌드와 실행, 장시간 구동.
- 생성 중 뺀 블록이 생성 뒤 남는 동작은 기존 RFID-SNAPSHOT-001 규칙을 유지한 것이며, 이번에 코드를 읽어 확인했을 뿐 영상 종료 후 홈 복귀까지 실제로 재현하지는 않았다.
