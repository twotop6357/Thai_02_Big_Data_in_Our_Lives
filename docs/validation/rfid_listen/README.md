## 최종 결과

- EditMode 114/114 PASS. 수신 포트 범위, 이전 version1 거부, 출발지 IP→칸 대응 테스트를 추가했다.
- `runtime.json`: Editor Play 55항목 PASS. 실제 TCP 소켓으로 `127.0.0.11~14` 출발지 IP 클라이언트 4개를 앱의 수신 포트에 접속시켰다.
  - 실제 설정으로 포트10123 수신, 미등록 IP 거부와 기존 연결 유지.
  - 포트 사용 중 보고와 포트가 비면 자동 복구.
  - 리더 미접속 칸의 블록이 3초 뒤에도 유지되고, 첫 접속도 블록을 지우지 않으며, 연결돼 있던 리더가 끊기면 비움.
  - 재접속, 같은 IP의 새 접속이 이전 연결을 대체하고 이전 연결 종료가 새 연결에 영향 없음.
  - 기존 항목(프레임 분할/합침, 그룹 우선, 생성 고정, 매핑 저장/교체/삭제, JSON 재로드, F9/F10 입력 격리) 유지.
- `f10_panel.png`: 수신 상태 줄과 네 칸 연결 상태를 직접 확인. 그림의 포트·IP·UID는 테스트 값이다.

## 실행과 보존

`Tools/RFID/verify_tcp_mapping.cs`를 Idle Play에서 Unity execute_code로 실행한다. 저장 테스트는 OS Temp의 `Thai02-RFID-TCP-validation/RfidSettings.json`에만 쓰고 종료 시 원래 설정·경로·입력 상태를 복원한다.

최종 콘솔의 오류/경고 9건은 모두 의도한 실패 주입 결과다(미등록 IP2, 포트 점유1, 잘못된 HEX, 미등록 블록, 문법 오류 JSON의 메시지와 예외).

## 중간 수정

첫 실행에서 `Listen failed` 경고에 OS 언어(한국어) 소켓 메시지가 들어가 영문 로그 규칙에 어긋났다. `SocketErrorCode`를 쓰도록 고친 뒤 EditMode와 Play를 다시 실행했고 위 결과는 수정 후 값이다.

## 미검증

- 실제 RFID 리더, 현장 망, Windows 방화벽 인바운드: 루프백은 방화벽을 거치지 않으므로 이 검증으로 확인되지 않는다.
- Keepalive: 소켓 옵션 적용 후 연결이 정상 동작함만 확인했다. 전원 차단 시 약 15초 감지는 계산값이며 측정하지 않았다.
- Windows Player 빌드와 실행, 장시간 구동. 기존 배포본(`Builds/`, Desktop/Thai_02)은 재빌드 전까지 이전 클라이언트 방식이다.
- 리더가 재접속 후 현재 카드를 다시 보고하는지 알 수 없다. 다시 보고하지 않으면 카드를 다시 올려야 인식된다.
