# 네트워크 RFID 리더와 F10 설정

RFID-STABLE-001 / 2026-11-02. `0_Idle`에서 시작하면 영속 RFID Hub에 TCP 수신기와 운영창을 하나씩 자동 연결한다. F10은 Comfy 준비 여부와 관계없이 사용 가능하다. 씬의 수동 편집은 필요 없다.

## 리더 위치와 JSON

프로젝트는 `Assets/StreamingAssets/RFID/RfidSettings.json`, 빌드는 `Thai02_Data/StreamingAssets/RFID/RfidSettings.json`을 사용한다. **앱이 PC의 TCP 포트(`listenPort`, 기본 10123)를 열고 리더가 TCP 클라이언트로 접속한다.** 앱은 리더에 먼저 접속하지 않는다. 접속한 장비의 출발지 IP로 칸을 정하므로 설정된 IP의 리더는 접속 순서와 관계없이 자기 칸에 자동 연결된다.

| slot | 위치 | 리더 IP |
|---|---|---|
| 0 | 좌상단 | 192.168.0.121 |
| 1 | 우상단 | 192.168.0.122 |
| 2 | 좌하단 | 192.168.0.123 |
| 3 | 우하단 | 192.168.0.124 |

수신 포트·리더 IP·패킷 해석·카드 매핑을 이 JSON에서 관리한다. 변경 후 F10의 `Reload JSON` 또는 재실행으로 적용한다. 잘못된 JSON은 오류를 표시하고 기존 정상 설정을 유지한다. 최초 로드 실패 시 수신을 시작하지 않는다. `enabled: false`는 수신을 끈다. 이전 클라이언트 방식의 `version: 1` 파일은 거부하므로 `version: 2`와 `listenPort`로 옮겨야 한다. 저장 폴더의 쓰기 권한이 필요하며 쓰기 실패는 창에 표시하고 이전 파일/매핑을 보존한다.

## 현장 네트워크 설정

1. **리더:** TCP 클라이언트 모드로 바꾸고, 목적지를 `PC IP:10123`으로, 자기 IP를 위 표의 값으로 설정한다. 끊겼을 때 자동 재접속하는 옵션이 있으면 켠다. 재접속은 리더의 기능이며 앱이 대신할 수 없다.
2. **PC:** 리더가 접속할 수 있도록 같은 대역의 고정 IP를 지정한다(`.121`~`.124` 제외). DHCP로 IP가 바뀌면 리더가 접속하지 못한다.
3. **Windows 방화벽:** 인바운드 허용이 필요하다. 관리자 PowerShell에서 한 번 실행한다. 첫 실행 때 뜨는 방화벽 확인창은 전체 화면 뒤에 가려질 수 있으므로 미리 등록한다.

```powershell
New-NetFirewallRule -DisplayName "Thai02 RFID" -Direction Inbound -Protocol TCP -LocalPort 10123 -RemoteAddress 192.168.0.121-192.168.0.124 -Action Allow
```

2026-11-18 DEPLOY-SELF-001: 프로그램을 껐다 켰을 때 이전 실행이 띄운 ComfyUI 서버가 수신 포트를 붙잡아 `Listen failed`가 계속되던 문제를 고쳤다([TS-20261118-01](TroubleShooting.md#TS-20261118-01)). 카드 매핑은 `StreamingAssets/RFID/RfidSettings.json`의 `cards`에 저장되며 배포본에서는 `NSM_DNA_02_Data/StreamingAssets/RFID/RfidSettings.json`이다. 새 배포본으로 바꿀 때 이 파일 하나를 옮기면 등록한 카드가 유지된다.

F10 맨 위 줄에 수신 상태가 표시된다. `Listening on TCP port 10123`이면 정상이다. `Listen failed`는 다른 프로그램이 포트를 쓰는 경우 등이며 2초마다 다시 시도한다. `Rejected IP`는 JSON에 없는 IP의 접속을 거부했다는 뜻이므로 리더 IP 설정을 확인한다.

## 카드 등록

1. F10으로 창을 열어 네 칸의 연결 상태·UID·수신 원문 HEX를 확인한다. 아직 완성 프레임이 없으면 `RX`로 최근 TCP 수신 바이트를 표시한다.
2. 카드를 올리고 해당 칸의 `Select current card`를 누른다. `Selected card HEX`에 직접 입력할 수도 있다. 선택 UID는 입력란에 고정되어 이후 다른 카드가 수신돼도 저장 대상이 바뀌지 않는다.
3. Group 4종·Product 10종·Color 6종 중 대응 블록을 고르고 `Save / replace mapping`을 누른다. 같은 UID는 교체하며 같은 블록에 여러 카드를 지정할 수 있다. 현재 올려둔 카드도 기존 그룹 우선 규칙에 따라 반영한다.
4. `Delete mapping`으로 해당 UID를 삭제한다. 아래 저장 목록을 누르면 UID를 선택한다. F10 또는 Close로 닫는다.

매핑은 언어 공통이며 실제 블록 이미지는 기존 Thai/English 설정을 따른다. 초기 JSON의 `cards`는 비어 있고 아래는 가상의 예시다.

```json
"cards": [
  { "uid": "001122AABBCCDD", "kind": "Group", "id": "child" },
  { "uid": "002233AABBCCDD", "kind": "Product", "id": "shoes" },
  { "uid": "003344AABBCCDD", "kind": "Color", "id": "red" }
]
```

HEX는 선행 0을 보존하고 대문자로 저장한다. 공백·콜론·하이픈은 제거한다. 홀수 자리·HEX 이외 문자·알 수 없는 블록 ID·중복 UID는 거부한다. 같은 폴더의 `.tmp`를 완성한 뒤 원본과 교체하고 직전 원본을 `.bak`에 보관한다. 백업 복원은 프로그램을 끄고 내용을 확인해 원본 JSON에 복사한다.

F10 중에는 전시 버튼 입력과 F9 창을 막고 네트워크 카드 상태는 계속 갱신한다. 닫은 뒤 새로 버튼을 눌러 진행한다. 이미지 생성 중에는 원래 네 블록 고정 규칙을 유지하며 F10은 조회만 가능하고 저장/삭제/재로드를 막는다. 생성 중 무시한 입력이나 그룹 이전에 무시된 비그룹 카드를 반복 보고만으로 뒤늦게 재생하지 않는다. 다시 올려 새 입력으로 사용한다.

## HEX 패킷 형식과 제거 신호

사용자 확인 사항은 **LAN-754(KA118) / TCP 클라이언트 / 10123 / 바이너리 HEX**다. 실제 7바이트 값이 반복 수신되는데 이전 설정이 16바이트씩 잘라 같은 카드가 7가지 값으로 순환하는 문제를 재현했다. 예전의 16바이트 예시는 장비의 프레임 길이 계약이 아니므로 기본 설정에서 고정 길이 분할을 제거했다.

기본 `UidBurst`는 TCP 조각을 모아 **마지막 바이트 이후 100ms 수신 공백**에서 완성 묶음으로 처리한다. 그 묶음이 같은 값의 정확한 반복이면 단일 값으로 합친다. 예를 들어 가상 UID `0504A1736922D5`가 두 번 들어와도 F10의 UID는 이 7바이트 한 개다. 7바이트로 고정한 것도 아니며, 4/7/10/16바이트를 실제 소켓으로 검증했다. 새로운 단일 값은 두 번 일치해야 선택 가능해지고, 한 묶음에 동일 값 두 개가 있으면 이 조건을 바로 만족한다. 이후 정상 반복은 기존 1초 유지 판정에 전달한다. 선행0/바이트 순서는 보존하고 임의의 헤더/체크섬 제거·정렬·회전 정규화는 하지 않는다. 제조사 UID 필드의 세부 계약은 확보하지 못했으므로 사용자 확인의 반복 값 전체를 식별자로 사용한다.

**현장 조건:** 공백은 TCP 패킷 경계가 아니다. 조각 사이 최대 지연보다 길고 장비의 보고 묶음 사이 공백보다 짧게 `idleGapMilliseconds`를 조정해야 한다. 공백 없이 영구히 연속 전송하는 모드 또는 한 묶음 안에서 서로 다른 카드가 섞이는 모드는 이 방법으로 경계를 보장할 수 없다. 이 경우 실제 프로토콜의 구분자/헤더·길이 필드로 명시적으로 구분해야 한다. 값 자체가 더 짧은 패턴의 반복인 특수 UID도 단순 반복 보고와 구별할 수 없으므로 `Delimiter` 등 경계가 명시된 모드를 쓴다. 길이 없는 임의 TCP 스트림에서 UID를 완전히 추론한다고 주장하지 않는다. 자원 보호 상한512바이트와 초과 묶음 폐기는 유지하며, 장비에 별도 조회 명령은 보내지 않는다.

| format 설정 | 용도 |
|---|---|
| `framing: "UidBurst"`, `idleGapMilliseconds: 100` | 새 기본값. 수신 공백까지 모으고 동일 반복을 단일 UID로 사용. `fixedFrameBytes`는 무시 |
| `framing: "FixedLength"`, `fixedFrameBytes: 16` | 명시적인 고정 길이 장비용 호환 모드. 현재 장비의 기본값으로 쓰지 않음 |
| `framing: "IdleGap"`, `idleGapMilliseconds: 100` | 필요할 때 수신 공백으로 프레임 구분. 연속 스트림 경계 보장 안 됨 |
| `framing: "Delimiter"`, `delimiterHex: "0D0A"` | CRLF까지 한 프레임, 구분자는 제외 |
| `asciiHex: false` | 바이너리 바이트 `00 AA` → HEX `00AA` |
| `asciiHex: true` | ASCII 문자열 `00AA`를 HEX로 해석 |
| `uidOffsetBytes: 0`, `uidLengthBytes: 0` | 디코딩 후 UID 시작/길이. 길이 0은 나머지 전체. 실제 헤더/체크섬을 제외하도록 조정 |
| `removedValues: []` | 추출된 값과 비교할 실제 제거 코드. 장비가 `00000000`을 보낸다고 확인된 경우에만 `["00000000"]` 지정 |

`Raw`에는 반복을 포함한 수신 묶음이 남고 **등록은 `UID` 또는 Select current card로 한다.** 예전의 잘린 16바이트 값을 저장했다면 새로운 UID로 다시 등록해야 한다. 기존 매핑을 임의 변환·삭제하지 않는다. 코드 DLL과 `framing`을 함께 적용하고 프로그램을 완전히 재시작한다. Desktop/Thai_02에는 적용했고, 다른 PC/USB에는 `RFID_Update.zip`을 실행파일 폴더에 풀어 `Apply_RFID_Update.cmd`를 실행한다. 기존IP/매핑/Comfy 설정 보존, 원본 DLL2개/JSON은 RFID_Backup_날짜에 백업한다. [검증/한계](validation/rfid_stable/README.md).

## 블록 유지 판단

리더에는 카드가 계속 올려져 있는지 알려 주는 기능이 없다. 그래서 앱이 일정 주기마다 그동안 들어온 값 중 **가장 최근 값**을 확인해 판단한다. 주기는 `StreamingAssets/RFID/RfidPresenceSettings.json`의 `checkIntervalMilliseconds`(기본 1000, 범위 100~60000)로 정한다. 변경 후 F10의 `Reload JSON` 또는 재실행으로 적용하며, 이 파일이 없거나 값이 잘못되면 오류를 표시하고 기존 정상 설정을 유지한다.

| 확인 시점의 값 | 판단 |
|---|---|
| 현재 값과 같음 | 블록 유지 |
| 현재 값과 다름 | 블록 교체 |
| 값이 없음(또는 `removedValues`의 값) | 블록 제거 |

- **주기는 리더의 실제 보고 간격보다 길게 잡는다.** 카드를 올려 두었는데 한 주기 동안 값이 한 번도 오지 않으면 제거로 판단한다. 보고 간격과 주기가 비슷하면 값이 없는 주기가 생겨 블록이 사라졌다 나타날 수 있다. F10의 `frames` 증가 속도로 실제 간격을 확인한다.
- 적용은 확인 시점에만 일어난다. 기본값에서 인식과 교체는 최대 약 1초, 제거는 최대 약 2초 걸린다.
- 잘못된 프레임은 값으로 치지 않는다. 그 주기에 다른 값이 없으면 제거로 판단한다.
- 한 번도 값을 보내지 않은 칸은 비우지 않는다. F9로 올린 블록도 리더가 같은 칸에 새 값을 보내거나 값이 사라지기 전까지 유지된다.
- 이미지 생성 중의 판단은 화면에 반영하지 않고 끝난 뒤 되풀이하지 않는다. 생성 중 뺀 블록은 다시 올렸다 빼기 전까지 화면에 남을 수 있다.

## 연결 끊김

연결이 끊기면 해당 칸을 비우고 나머지 세 연결은 유지하며 리더가 다시 접속하기를 기다린다. 같은 IP로 새 접속이 오면 이전 연결을 닫고 새 연결을 쓴다. 이때 카드 상태를 알 수 없으므로 칸을 비우고 다음 보고로 복구한다. 리더가 전원 차단 등으로 말없이 사라지면 TCP keepalive로 약 15초 뒤 끊김으로 처리하도록 설정했다(실제 장비 미검증). 생성 잠금 중에는 단절도 선택에 반영하지 않는다.

접속한 적 없는 칸은 비울 이유가 없으므로 F9 시뮬레이터로 올린 블록이 유지된다. 연결돼 있던 리더가 끊기면 그 칸의 블록은 어떻게 올렸든 비운다.

최대 프레임 512바이트·대기열 256개 제한. 과대/잘못된 프레임은 카드로 쓰지 않고 대기열 초과 시 연결을 다시 시작한다. 카드 HEX를 기본 실행 로그나 외부 운영 로그 API로 전송하지 않는다.

검증과 화면 증거: [validation/rfid_listen/README.md](validation/rfid_listen/README.md). 이전 클라이언트 방식 기록은 [validation/rfid_tcp/README.md](validation/rfid_tcp/README.md)에 보존한다. 현장에서 실제 네 리더의 클라이언트 접속·프레임·UID 고정성·제거·재접속 확인이 필요하다.
