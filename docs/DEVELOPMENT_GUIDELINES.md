# Unity 개발·성능 기준

적용 범위: Unity 2022.3.62f3 / Windows 전시·키오스크. 공동 작업 절차는 [AGENTS.md](../AGENTS.md), 현재 작업은 [HANDOFF](agents/HANDOFF.md)를 따른다.

## 설계와 C#

- 가장 단순하게 실패 경로까지 설명할 수 있는 구현을 선택한다. 기존 VContainer·UniTask·MessagePipe·R3·DOTween을 우선 활용하되 실제 설치 API를 확인한다. 새로운 전역 싱글톤·프레임워크·추상화를 필요 없이 추가하지 않는다.
- 화면 상태와 전환 책임을 명시한다. 연타·중복 이벤트·늦은 응답으로 전환이 겹치지 않도록 진입 가드나 상태 검사를 둔다. 복귀·취소·해제는 반복 호출해도 안전해야 한다.
- 참조는 직렬화 필드나 주입으로 명확히 전달한다. 필수 참조 누락은 초기화 시 진단하고 안전한 화면으로 처리한다. 핫패스에서 Find·리플렉션·반복 GetComponent를 피한다.
- Unity 2022.3의 컴파일러와 API 호환성을 확인한다. 데스크톱 최신 .NET용 예제를 그대로 적용하지 않는다. 기존 네임스페이스·명명·코드 스타일을 따른다.
- Inspector 데이터가 있는 클래스·필드 이름 변경 시 직렬화 호환성과 기존 씬·프리팹을 확인하고 필요하면 `FormerlySerializedAs` 등 마이그레이션을 적용한다.
- 조용한 예외 삼키기, 무조건적인 null 무시, 무한 재시도는 피한다. 사용자에게 복구 경로를 제공하고 로그에는 원인을 찾을 최소 문맥을 남긴다.

## GC와 관리 메모리

- 목표는 **워밍업 후 반복되는 프로젝트 핫패스의 지속적인 할당을 가능한 0 B/frame에 가깝게 줄이는 것**이다. 초기화·화면 진입·네트워크 응답의 필요한 할당까지 금지하지 않는다. 실측 없이 앱 전체의 0 GC를 보장하지 않는다.
- Update·LateUpdate·FixedUpdate·반복 콜백에서 매번 생성하는 배열·List·문자열, LINQ의 임시 컬렉션, 박싱, 캡처 람다와 델리게이트 생성을 검토한다. 값이 바뀔 때 UI를 갱신하고 용량을 정한 버퍼를 재사용한다.
- `foreach` 자체를 일괄 금지하거나 `struct`로 바꾸면 항상 빨라진다고 가정하지 않는다. 실제 타입·인터페이스 변환·복사 비용과 Profiler 결과로 판단한다.
- 리스트 재사용 시 참조를 정리하고 과도한 최대 용량을 영구 보유하지 않는다. 정적 캐시, 이벤트, 딕셔너리, 로그, 대기열은 크기 제한·만료·초기화 책임을 둔다.
- 빈번한 생성·파괴가 확인된 대상에만 `UnityEngine.Pool` 등 기존 풀을 적용한다. 최대 보유량, 이중 반환 방지, 반환 시 구독·Tween·타이머·선택 상태 초기화, 종료 시 제거를 구현한다. 화면마다 큰 풀을 무조건 만들지 않는다.
- `GC.Collect()`나 GC 비활성화를 주기적 끊김의 기본 해결책으로 사용하지 않는다. GC 설정 변경은 측정 근거와 장시간 메모리 검증이 있는 별도 변경으로 취급한다.
- 로그 문자열과 직렬화도 할당을 만든다. 매 프레임·센서 샘플마다 로그를 남기지 말고 수준·샘플링·빈도 제한과 파일 보존 정책을 적용한다. 장애 시 같은 오류가 무한 누적되지 않게 한다.

## Unity 객체·네이티브 자원

- GC는 Unity 네이티브·GPU 자원을 모두 정리하지 않는다. 생성한 Texture·Material·Mesh·RenderTexture와 스트림·소켓·요청·시리얼 포트의 소유자와 해제 경로를 정한다.
- `renderer.material` 등의 암묵적 복제를 주의한다. 공유 Material·원본 에셋을 런타임에 임의로 변경하지 않는다. 필요한 경우 MaterialPropertyBlock 등 실제 렌더링 방식과 호환되는 방법을 검토한다.
- 임시 RenderTexture는 대응하는 API로 반환하고, 직접 생성한 객체는 사용 중 참조를 끊은 뒤 적절히 Release/Destroy한다. Addressables 핸들은 소유자가 대응하는 해제를 수행한다. Unity 소유 에셋을 임의로 파괴하지 않는다.
- 영상·음향·Tween·코루틴·구독은 화면 종료 시 정지·해제한다. DOTween은 대상/ID별로 정리하고, 다른 화면의 Tween을 끊는 전역 Kill을 사용하지 않는다. 풀링 대상은 비활성화 때도 정리한다.
- 정적 참조와 DontDestroyOnLoad 객체가 씬 UI·큰 에셋·이벤트 구독을 붙잡지 않게 한다. Domain Reload 비활성 환경에서 정적 상태가 남는지도 관련 변경 시 확인한다.

## 비동기·이벤트·스레드

- 사용자 세션/화면/앱의 수명을 구분한다. 파괴 토큰만으로 화면 숨김·비활성화가 취소된다고 가정하지 않는다. 화면 작업에는 별도 취소 범위를 두고 종료 시 취소·완료 처리를 거쳐 CTS를 해제한다.
- 토큰은 실제 하위 요청·대기까지 전달한다. 취소를 지원하지 않는 작업은 화면 세대 ID나 요청 버전으로 늦은 결과를 무효화한다. 완료 후 Unity 객체 생존 여부와 현재 화면을 확인한다.
- 기본적으로 UniTask를 사용하되 API 요구에 맞게 Task와 연결한다. UniTask의 동일 인스턴스를 임의로 여러 번 await하지 않는다. `async void`는 프레임워크가 요구하는 이벤트 진입점에 한정하고 내부 예외를 처리한다. fire-and-forget은 예외 관찰과 취소 책임이 있을 때만 사용한다.
- `.Wait()`, `.Result`, 메인 스레드의 Thread.Sleep·동기 네트워크/대용량 파일 I/O로 UI를 막지 않는다. Unity 객체·UI API는 메인 스레드에서 다룬다. 작업 스레드는 순수 데이터 처리로 범위를 제한한다.
- 구독 시작/종료를 대칭으로 맞춘다. 활성 수명이면 OnEnable/OnDisable, 객체 수명이면 생성/파괴에 맞추고 중복 구독을 방지한다. 해제할 델리게이트를 보관하며 기존 base 호출 순서와 주입 시점을 실제 코드로 확인한다.
- 센서·시리얼 콜백의 데이터를 제한된 큐로 전달하고 메인 스레드에서 적용한다. 폭주 시 버리기/합치기 정책, 연결 해제 시 복구와 종료 처리를 명시한다.

## API·설정·파일

- 요청마다 시간 제한과 취소, 재시도 상한·지연을 둔다. 저장/결제 등 부작용 요청은 서버의 멱등성 계약 없이 자동 재시도하지 않는다. 인증·스키마 오류를 무조건 재시도하지 않는다.
- 응답의 null·빈 값·크기·범위를 검증하고 성공한 최신 결과만 적용한다. 오프라인·실패 시 재시도/취소/첫 화면 복귀 등 사용자가 빠져나갈 경로를 둔다.
- 설정을 받기 전에는 준비 상태를 명시하고 이벤트/제공자를 통해 적용한다. 잘못된 값은 범위 검사와 진단을 거친다. 기본 설정과 오류 시 대체 설정을 구분한다.
- 사용자 데이터 저장은 요구사항에 맞게 `Application.persistentDataPath` 등을 사용한다. 쓰기 실패·디스크 부족을 처리하고, 중단 시 파일이 손상되지 않도록 같은 볼륨의 임시 파일과 교체 등 검증된 저장 방식을 사용한다.
- API 키는 승인된 외부 설정/자격 증명 경로로 제공한다. 배포 클라이언트에 포함된 값은 비밀 보관소가 아님을 고려하고 서버 측 중계를 검토한다. 문서·로그에는 실제 자격 증명을 기록하지 않는다.

## 에셋·패키지·변경 관리

- Assets의 파일 이동·이름 변경·삭제 시 `.meta`를 함께 관리하고 기존 GUID를 보존한다. 새 에셋의 메타 생성과 참조 연결을 확인한다. 씬/프리팹 YAML은 가능한 Unity 도구로 변경하고 텍스트 수정 시 참조와 diff를 검증한다.
- Library·Temp·Logs·자동 생성 솔루션·빌드 결과를 소스 변경으로 섞지 않는다. 에디터가 자동 변경한 파일은 원인을 확인하고 작업자가 만든 것만 구분해 처리한다.
- UPM/NuGet DLL, asmdef, 플랫폼 Import Settings와 Roslyn의 Editor 제한을 함께 확인한다. 네이티브/직렬화/AOT 관련 변경은 대상 Player 빌드에서 확인한다.
- 신규 기능에만 필요한 UI·Sound·Video·Fade·Arduino 컴포넌트를 배치한다. 패키지가 존재한다는 사실을 씬 설정 완료로 간주하지 않는다.

## 검증 기준과 성능 기록

- 변경 위험에 맞게 EditMode의 순수 로직, PlayMode의 생명주기·화면 전환, Windows Player 검증을 선택한다. 실제 위험을 확인하는 테스트를 작성하고 구현을 그대로 복제한 테스트나 사소한 문서 변경용 테스트는 만들지 않는다.
- 복귀·연타·반복 진입·취소 직후 응답·미디어 종료·무입력 Pause/Resume·설정 오류·API 실패·장비 단절·재연결·재실행 중 관련 경로를 확인한다. 자동 PC 종료는 실제 명령 없이 어댑터/모의 실행으로 검증한다.
- 성능은 대상 PC의 Development Player와 Unity Profiler/Memory Profiler 등으로 측정한다. Editor 측정과 Player 결과를 구분하고 Deep Profile의 오버헤드를 고려한다.
- 워밍업 후 동일 시나리오의 프레임 시간, GC Alloc, GC 스파이크, 관리/네이티브/GPU 메모리 및 객체·구독 수 추이를 비교한다. 정리·안정화 시점을 맞춰 반복 전후를 비교하고 메모리가 계속 증가하면 원인을 조사한다.
- 현재 설정의 60 FPS는 목표값일 뿐 보장된 성능이 아니다. 목표 프레임 시간(60 FPS라면 약 16.7ms), 화면 해상도, 빌드 설정, 반복 횟수와 장시간 구동 시간은 대상 장비·콘텐츠에 맞춰 정하고 기록한다. 측정하지 않은 수치를 합격으로 적지 않는다.
- HANDOFF에 환경·시나리오·실행 방법·결과·증거 위치·미수행 사유를 남긴다. 로그/캡처에는 비밀·개인정보를 제거한다. 설치 PC API·장비·장시간 검증이 남으면 배포 검증 미완료로 표시한다.

## 공식 참고

프로젝트 지침은 공식 문서의 일반 원칙을 이 프로젝트에 적용한 기준이다. API 사용 전 설치 버전과 실제 구현을 확인한다.

- [Unity 2022.3 GC best practices](https://docs.unity3d.com/2022.3/Documentation/Manual/performance-garbage-collection-best-practices.html): 임시 할당·문자열·박싱·컬렉션 재사용·풀링 검토 근거.
